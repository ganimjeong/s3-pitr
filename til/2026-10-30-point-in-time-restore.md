# 시점 복구와 검증 회고

시점 복구(`restore.py`), 복구 검증(`verify.py`), 명령줄 도구(`__main__.py`), 통합 시험(`e2e/`)을 만든 작업.

## 한 줄 요약

복구에서 가장 위험한 건 실패가 아니라 "그럴듯하게 틀린 복구"임. 그래서 순서를 알 수 없으면 멈추고, 검증은 빠진 것과 남는 것을 둘 다 봄.

## 1. 같은 초 안의 순서를 알 수 없음

- 이슈: freezegun으로 시각을 고정해 moto 동작을 확인하다가, 같은 초에 덮어쓰기와 삭제를 하면 `ListObjectVersions` 결과만으로는 무엇이 나중인지 알 수 없다는 걸 봄
- 원인 찾기
  - S3 `LastModified`는 초 단위임
  - S3 응답 XML은 `Version`과 `DeleteMarker`를 시간 순서대로 섞어서 줌. 그런데 boto3는 이걸 `Versions`, `DeleteMarkers` 두 목록으로 나눠서 돌려줘서 둘 사이의 순서가 사라짐
  - 그래서 "02:00:00에 덮어쓰고 지움"과 "02:00:00에 지우고 다시 씀"을 구분할 수 없음. 앞은 그 시각에 객체가 없고, 뒤는 있음
- 고민한 방법
  - 삭제 표시가 항상 나중이라고 가정: 흔한 순서지만 틀리면 있어야 할 객체가 조용히 빠짐
  - 백업할 때 목록 순서를 번호로 저장: 버전끼리는 되지만 버전과 삭제 표시 사이 순서는 이미 boto3에서 사라져서 안 됨
  - 원본 XML을 직접 파싱: botocore 응답 파서를 우회해야 해서 유지보수 부담이 큼
- 결정: 그 시각의 마지막 기록이 같은 초에 두 개 이상이면 `AmbiguousRestorePointError`로 멈추고 키 목록을 알려 줌. 1초 앞이나 뒤 시각으로 다시 하면 됨. 그 뒤에 더 늦은 기록이 있으면 순서가 상관없으니 멈추지 않음
- 재발 방지: CONTRIBUTING 그라운드 룰 7번 "알 수 없는 것은 추측하지 않고 멈춤"
- 배운 점: SDK가 응답을 편하게 바꿔 주는 과정에서 정보가 사라질 수 있다. 정답이 필요한 판단은 SDK 결과가 원래 응답의 어떤 정보를 버렸는지부터 확인한다

## 2. 복구는 빈 버킷으로만

- 결정: 원본 버킷으로는 복구하지 않음. 대상 버킷이 비어 있지 않으면 시작하지 않음
- 이유
  - 원본에 덮어쓰면 복구가 잘못됐을 때 되돌릴 곳이 없음
  - 대상에 다른 객체가 있으면 검증에서 "남는 객체"가 복구 잘못인지 원래 있던 건지 구분할 수 없음
- 배운 점: 복구 도구의 안전장치는 "되돌릴 수 있는가"와 "검증할 수 있는가" 두 질문으로 정한다

## 3. 검증은 빠진 것과 남는 것을 둘 다 봄

- 고민: 처음에는 계획에 있는 키마다 체크섬만 비교하려 했음. 그러면 그 시각 뒤에 생긴 객체가 대상에 섞여 있어도 통과함
- 결정: 대상 버킷 전체 목록을 받아서 계획에 없는 키는 `unexpected`, 계획에 있는데 없는 키는 `missing`, 체크섬이 다르면 `mismatched`. 셋 중 하나라도 있으면 실패, 명령줄 종료 코드 1
- 확인: 남는 객체 검사를 일부러 지우면 시험이 실패함

## 4. 변이로 확인한 것

시험 14개가 처음부터 통과해서 보장을 하나씩 깨 봄. 다섯 개 모두 시험이 잡았음.

| 깬 보장 | 실패한 시험 수 |
| --- | --- |
| 같은 초면 멈춤 | 1 |
| 마지막 기록이 삭제 표시면 뺌 | 2 |
| 복구 시각과 같은 초의 기록도 포함 | 8 |
| 남는 객체도 실패로 봄 | 1 |
| 비어 있지 않은 대상은 거부 | 1 |

지난 회고(증분 백업)에서 실패를 넣는 위치를 잘못 골라 보장 하나가 비어 있었던 걸 겪어서, 이번에는 시험을 쓰기 전에 보장 목록부터 적었음.

## 5. 통합 시험은 HTTP로

- 결정: 단위 시험은 `mock_aws`(프로세스 안에서 가로챔), 통합 시험은 moto를 HTTP 서버로 띄우고 `AWS_ENDPOINT_URL`만 바꿈. 코드는 엔드포인트를 모르고, 실제 AWS와 같은 경로(HTTP 요청, 응답 파싱, 재시도)를 탐
- 시나리오: 객체 200개 백업 → 50개 덮어쓰기와 30개 삭제 → 다시 백업 → 두 시점으로 각각 복구하고 검증. 변조한 복구는 `verify`가 종료 코드 1을 냄
- 같은 초 문제를 피하려고 단계 사이에 1.1초씩 기다림. 그래서 통합 시험이 47초 걸림. freezegun은 moto 서버 스레드의 시계까지 바꿀 수 있지만, 통합 시험에서 시계를 바꾸면 실제 환경과 달라져서 쓰지 않음

## 남은 고민

- 복구 계획을 만들려고 카탈로그 전체를 읽음. 키 수억 개면 느림. 정렬 키에 시각을 넣으면 범위 조회로 줄일 수 있지만 같은 초 문제 때문에 지금 구조를 유지함
- 복구는 객체를 하나씩 순서대로 복사함. 객체가 많으면 병렬로 나눠야 함. `bulk_restore`는 Step Functions 분산 Map으로 나눔(research/01)
- 실제 S3와 moto의 차이(체크섬, Object Lock)는 아직 실제 AWS에서 확인하지 않음
