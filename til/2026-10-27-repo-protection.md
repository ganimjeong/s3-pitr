# 첫 푸시와 저장소 보호 설정 회고

뼈대를 main에 올리고 서명, 머지 방식, main 보호 규칙을 건 작업. 그 과정에서 dependabot 운영 방식을 세 번 바꿈.

## 한 줄 요약

"모든 커밋은 내 계정으로"라는 규칙을 지키려면 봇과 GitHub이 만드는 커밋까지 봐야 함. 회사(`terraform-provider-clumio`)처럼 dependabot PR은 알림으로만 쓰고 반영은 내 계정으로 하니 예외가 필요 없었음.

## 1. 서명은 했는데 Verified가 안 될 뻔함

- 이슈: 커밋은 SSH 키로 서명해 뒀지만 GitHub 계정에는 서명용 키가 등록돼 있지 않았음. 인증용 키와 서명용 키는 GitHub에서 따로 등록함
- 원인 찾기: `gh` 토큰에 `admin:ssh_signing_key` 권한이 없어서 등록 API가 404를 돌려줌
- 해결: 권한을 받은 뒤 같은 키를 서명용으로 등록하고 나서 푸시함. GitHub은 푸시한 시점에 서명을 검증해서 기록하므로, 키 등록 전에 올리면 나중에 등록해도 Unverified로 남을 수 있음
- 확인: 커밋 7개가 전부 작성자 `ganimjeong`, `verified=true`인지 API로 봄
- 로컬에서 `git log --show-signature`가 `allowedSignersFile` 오류를 냄. SSH 서명은 GPG와 달리 "누구의 키인지"를 로컬 파일로 알려 줘야 검증함. 레포 안 `.git/allowed_signers`에 내 이메일과 공개 키를 적어서 해결함
- 배운 점: 서명은 만드는 것과 검증되는 것이 다른 단계다. 검증할 쪽(GitHub, 로컬)에 키가 먼저 있어야 한다

## 2. dependabot을 어떻게 쓸까: 세 번 바꿈

- 이슈: 첫 푸시 직후 dependabot이 Actions 버전 업데이트 PR 3개(#3, #4, #5)를 열었음. 처음 넣을 때 옛 버전(v4, v5)을 적었기 때문임
- 첫 번째 판단: squash merge하면 main 커밋 작성자가 `dependabot[bot]`이 됨. "모든 커밋은 내 계정으로"라는 규칙과 부딪혀서 `dependabot.yml`을 지우고 봇 PR을 닫음
- 두 번째 판단: 회사가 쓰는 도구를 직접 써 보는 것도 이 레포의 목적이라서 dependabot을 되살리고, 봇 PR은 머지하기로 함. 봇 커밋만 예외로 두려고 했음
- 원인 찾기: 닫은 봇 PR을 다시 열려고 `@dependabot reopen`을 달았는데 반응이 없었음. 타임라인을 보니 PR을 닫을 때 dependabot이 브랜치를 지워서(`head_ref_deleted`) 다시 열 대상이 없었음. 다른 방법을 찾다가 "회사는 dependabot 설정을 어떻게 했나"를 보려고 Clumio 레포를 다시 열었는데, 내가 조사에서 `clumio-python-sdk`가 dependabot을 쓴다고 적은 게 틀린 걸 알게 됨. 두 레포의 `.github` 목록을 한 번에 조회하다가 결과가 섞였었음. 실제로 쓰는 레포는 `terraform-provider-clumio` 하나였음
- 더 보니 그 레포는 dependabot PR 9개 중 머지한 게 0개임. main 작성자는 전부 사람이고, 업데이트는 사람이 만든 Release PR에 "Updated dependencies."로 들어감
- 세 번째 결정: 회사와 같은 방식으로 함
  - dependabot은 켜 둠. 봇 PR은 새 버전이 나왔다는 알림임
  - 반영은 내 계정 커밋으로 하고, 반영한 뒤 봇 PR을 닫음
  - 이렇게 하면 "회사 도구를 써 본다"와 "모든 커밋은 내 계정으로"가 둘 다 지켜짐. 처음에 둘이 부딪힌다고 본 건 회사가 봇 PR을 머지할 거라고 짐작했기 때문임
  - 이번 반영: #3, #4, #5의 checkout, setup-python, upload-artifact v7 (PITR-8)
- 확인 실수 두 개
  - 조사 결과가 섞인 것: 레포 이름을 확인하지 않고 출력 한 덩어리를 한 레포 것으로 읽었음. 조사 문서를 고침
  - 셀프 리뷰에 "v7은 Node 런타임이 바뀐 업데이트"라고 확인 없이 적었음. 릴리스 노트를 보니 Node 24 전환은 v5~v6이고 v7은 ESM 전환과 의존성 업데이트였음. 댓글을 고침
- 재발 방지: 조사 문서의 [공개] 항목은 레포 이름과 파일 경로를 같이 적음. 여러 레포를 한 명령으로 조회할 때는 줄마다 레포 이름을 찍음
- 배운 점
  - 회사 방식을 따라 할 때는 "어떤 도구를 쓰나"에서 멈추지 말고 "그 도구의 결과를 어떻게 처리하나"까지 본다. 같은 도구라도 운영 방식이 다르면 다른 이력이 남는다
  - 짐작으로 규칙 충돌을 판단하지 않는다. 충돌한다고 느끼면 실제 사례부터 찾는다
  - 봇 PR을 닫으면 브랜치가 사라진다. 닫기 전에 다시 쓸 일이 있는지 먼저 본다

## 3. main 보호 규칙

- 결정
  - 머지는 squash만 허용함. 커밋 제목은 PR 제목, 본문은 PR 본문으로 씀. main 이력이 PR 하나당 커밋 하나가 되고 끝에 `(#번호)`가 붙음
  - 규칙: 삭제 금지, 강제 푸시 금지, 선형 이력, 서명 필수, PR 필수, CI 통과 필수, 리뷰 스레드 해결 필수
  - 승인 인원은 0으로 둠. 혼자 하는 레포에서 1로 두면 내 PR을 내가 승인할 수 없어서 머지가 막힘. 대신 PR마다 셀프 리뷰 댓글로 고른 방법과 버린 방법을 남김
- 순서: 첫 커밋들을 main에 올린 다음에 규칙을 걸었음. 먼저 걸면 main이 비어 있는 상태에서 PR을 만들 대상 브랜치가 없음
- 배운 점: 보호 규칙은 "무엇을 막을까"보다 "막은 뒤에도 일이 되는가"를 같이 봐야 한다

## 4. pre-commit의 ruff 훅이 legacy alias로 나옴

- 이슈: `pre-commit run --all-files` 결과에 `ruff (legacy alias)`가 찍힘. 통과는 했음
- 원인 찾기: `bulk_restore`는 ruff-pre-commit v0.14.0에서 `id: ruff`를 씀. 이후 버전에서 훅 id가 `ruff-check`로 바뀌고 `ruff`는 옛 이름으로만 남음
- 해결: `id: ruff-check`로 바꿈
- 배운 점: 회사 설정을 복사할 때는 그 설정이 쓰는 도구 버전도 같이 본다. 나는 더 새 버전을 쓰고 있어서 이름이 바뀐 걸 그대로 가져올 뻔했음
