# 초기 세팅 회고

레포 뼈대, 도구 설정, `common.py`를 만든 작업. 설정 파일은 `clumio-code/bulk_restore`를 거의 그대로 따랐음.

## 한 줄 요약

회사 설정을 그대로 가져와도 내 환경(Python 버전, Docker 유무)과 내가 쓰는 SDK(boto3)에 맞지 않는 부분은 그대로 쓰면 안 됨. 무엇을 따라 하고 무엇을 바꿨는지를 이유와 같이 남김.

## 1. Python 버전이 회사와 다름

- 이슈: 로컬 `python3`가 3.15였음. 그대로 쓰면 `target-version = 'py312'`인 Ruff와 실제 실행 버전이 달라짐
- 판단: 3.12 이후 문법을 실수로 써도 로컬에서는 돌아가고 Lambda 런타임(3.12)에서만 깨질 수 있음
- 해결: `uv python install 3.12`로 3.12를 따로 깔고 가상 환경을 3.12로 만듦. CI도 3.12로 고정함
- 배운 점: 버전은 "내 컴퓨터에 있는 것"이 아니라 "코드가 돌 곳"에 맞춘다

## 2. 재시도를 어디에 둘까

- 고민: `bulk_restore`는 urllib3 `Retry`(8번, 백오프 계수 2)로 HTTP 어댑터를 감쌈. 이 레포도 같은 방식으로 감쌀지
- 원인 찾기: `bulk_restore`가 감싸는 건 Clumio REST API를 부르는 `requests` 세션임. 이 레포는 boto3를 쓰는데, botocore에는 이미 재시도가 있음(기본 `legacy` 모드, 최대 5번). 그 위에 8번짜리 재시도를 또 감싸면 한 요청이 최악의 경우 40번 나감. 스로틀링(429, SlowDown) 상황에서 요청이 줄어야 할 때 오히려 늘어남
- 결정: 재시도는 botocore 설정 하나에만 맡김. 모드는 `adaptive`. 실패한 요청을 다시 보내는 것뿐 아니라 스로틀링 응답을 보면 클라이언트 쪽 요청 속도도 낮춤. 대량 복사를 하는 백업 도구에 맞음
- 주의: boto3 문서는 `adaptive`를 실험 단계 모드라고 적어 둠. 동작이 바뀔 수 있어서 boto3 버전을 `==`로 고정하고, dependabot이 boto3 새 버전을 알리면 버전을 올리는 PR에서 재시도 시험이 같이 돌게 함
- 재발 방지: CONTRIBUTING 그라운드 룰 1번에 "재시도 루프를 또 감싸지 않음"을 넣음. `client_config()`를 모든 클라이언트가 쓰게 하고 시험으로 모드를 고정함
- 배운 점: 회사 코드에서 가져올 것은 값(8번, 계수 2)보다 이유(일시적인 오류만 재시도하고 원인은 숨기지 않음)다

## 3. 카탈로그 정렬 키에 isoformat을 쓰면 안 되는 이유

- 고민: 카탈로그 정렬 키에 시각을 넣어서 "이 시각 이전의 최신 버전"을 범위 조회로 찾을 계획임. 문자열 순서와 시간 순서가 같아야 함
- 확인: `datetime.isoformat()`으로 직접 비교해 봄
  - 마이크로초가 0이면 `.000000`을 생략함. `09:00:00+00:00`과 `09:00:00.000001+00:00`은 `+`가 `.`보다 앞이라 우연히 순서가 맞음
  - 시간대가 섞이면 깨짐. 서울 17:00(UTC 08:00)은 UTC 09:00보다 이른데 문자열로는 `17:00:00+09:00`이 더 큼
- 결정: 항상 UTC로 바꾸고 마이크로초까지 자리를 고정한 `%Y-%m-%dT%H:%M:%S.%fZ`를 씀. 시간대 없는 `datetime`은 어느 시각인지 알 수 없으므로 받지 않고 예외를 던짐
- 재발 방지: 문자열 정렬 결과와 시간 순서가 같은지, 서울 시각이 UTC로 바뀌는지, 시간대 없는 값을 거부하는지 시험으로 고정함
- 배운 점: 우연히 맞는 것과 보장되는 것은 다르다. 정렬 키처럼 나중에 바꾸기 어려운 형식은 처음에 보장을 시험으로 박아 둔다

## 4. botocore Config의 retries가 타입 스텁에 없음

- 이슈: 시험에서 `client_config().retries`를 읽었더니 mypy가 `"Config" has no attribute "retries"`로 실패함. 시험 자체는 통과함
- 원인 찾기: botocore `Config`는 생성자 인자를 받아서 속성을 동적으로 만듦. 스텁은 생성자 인자만 정의하고 속성은 정의하지 않음
- 해결: 시험에서만 `getattr(config, 'retries')`로 읽고 이유를 주석으로 남김. `type: ignore`를 쓰지 않은 이유는 무시가 너무 넓어서임. 같은 줄의 다른 타입 오류까지 가려짐
- 배운 점: 시험 통과와 타입 검사 통과는 따로 확인한다. CI 순서가 mypy를 시험보다 먼저 두는 이유이기도 함

## 5. 로컬에 Docker가 없음

- 이슈: 통합 시험을 LocalStack으로 돌릴 계획이었는데 이 컴퓨터에 Docker가 없음
- 판단: Docker를 깔아서 맞출 수도 있지만, 시험이 특정 도구에 묶이는 것 자체가 문제임. boto3는 `AWS_ENDPOINT_URL` 환경 변수를 직접 읽으므로 코드는 엔드포인트를 몰라도 됨
- 결정: 통합 시험은 `AWS_ENDPOINT_URL`이 있으면 그걸 쓰고, 없으면 moto 서버를 시험 안에서 띄움. CI에서는 LocalStack 서비스 컨테이너를 붙여서 같은 시험을 한 번 더 돌릴 계획이었음(나중에 LocalStack이 토큰을 요구해서 moto로 바꿈. [증분 백업 회고](2026-10-30-incremental-backup.md) 참고)
- 배운 점: 엔드포인트를 코드가 아니라 환경이 정하게 하면, 시험 환경을 바꿔도 코드가 바뀌지 않는다

## 남은 고민

- moto가 실제 S3와 다르게 동작하는 부분(Object Lock, 체크섬)이 있을 수 있음. 마지막에 실제 AWS에서 한 번 돌려서 차이를 기록할 계획
