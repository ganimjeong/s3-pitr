# 증분 백업 회고

카탈로그(`catalog.py`), 증분 백업(`backup.py`), 시험 환경 도구(`envkit.py`)를 만든 작업. 원본 버킷의 버전 중 아직 백업하지 않은 것만 금고로 복사하고 DynamoDB에 기록함.

## 한 줄 요약

백업은 "다시 돌려도 같은 결과"가 핵심임. 그걸 지키는 건 코드 한 줄이 아니라 순서(복사 먼저, 기록 나중)와 두 겹의 중복 방지(이미 아는 버전 건너뛰기, 조건부 쓰기)였음. 그리고 그 보장 중 하나는 시험이 처음엔 지키지 않고 있었음.

## 1. 복사와 기록 중 무엇을 먼저 할까

- 고민: 버전 하나를 백업하려면 금고로 복사하고 카탈로그에 기록하는 두 단계를 거침. 둘 사이에서 프로세스가 죽을 수 있음
- 판단
  - 기록을 먼저 하면: 기록 후 복사 전에 죽었을 때 카탈로그에는 있는데 금고에는 없는 백업이 남음. 다음 실행은 "이미 아는 버전"이라 건너뛰므로 영원히 안 고쳐짐. 복구할 때에야 드러남
  - 복사를 먼저 하면: 복사 후 기록 전에 죽었을 때 금고에 기록 안 된 파일이 하나 남음. 다음 실행은 카탈로그에 없으니 같은 위치에 다시 복사하고 기록함. 금고 위치를 버전마다 고정(`vault/<버킷>/<키>/<버전 ID>`)해 둬서 다시 복사해도 덮어쓸 뿐임
- 결정: 복사가 먼저. 남는 게 "덮어쓸 파일"이면 괜찮고 "없는 백업"이면 안 됨
- 배운 점: 두 단계 작업에서 순서는 "멈췄을 때 무엇이 남는가"로 정한다. 남는 것이 다음 실행에서 저절로 고쳐지는 쪽을 고른다

## 2. 시험이 처음부터 다 통과함

- 이슈: 백업 시험 8개가 첫 실행에 전부 통과함. 규칙대로 보장을 하나씩 깨 봄
- 변이 결과
  - 이미 아는 버전 건너뛰기를 지움 → 1개 실패. 중복 기록은 조건부 쓰기가 한 번 더 막아서, 복사만 한 번 더 일어남. 막는 장치가 두 겹이라는 걸 이때 확인함
  - 재시도를 끔(`max_attempts=1`) → 스로틀링 시험 실패
  - 기록을 복사보다 먼저로 바꿈 → **전부 통과**. 1번에서 가장 중요하다고 한 보장을 지키는 시험이 없었음
- 원인 찾기: 중단 시험이 카탈로그 `put`에서만 죽게 만들었음. 기록 단계에서 죽으면 순서가 어떻든 결과가 같아서 순서를 구분하지 못함
- 해결: 복사(`copy_object`) 도중에 죽는 시험을 따로 만들고, "카탈로그의 모든 항목은 금고에 파일이 있다"를 직접 확인함. 같은 변이를 다시 넣어서 이 시험이 실패하는 것까지 봄
- 배운 점: 실패를 넣는 위치가 시험이 구분할 수 있는 것을 정한다. 보장마다 "이게 깨지려면 어디서 죽어야 하나"를 먼저 묻고 그 자리에 실패를 넣는다

## 3. 스로틀링을 어떻게 흉내 낼까

- 고민: moto는 S3를 흉내 내지만 스로틀링(503 SlowDown)은 내지 않음. `mock.patch`로 `copy_object`가 예외를 던지게 하면 botocore 재시도를 거치지 않아서, 시험하려던 "재시도는 botocore에 맡긴다"를 확인할 수 없음
- 결정: botocore의 `before-send` 이벤트에 핸들러를 걸어 처음 두 번은 503 응답을 돌려줌. 그러면 실제 HTTP 응답처럼 botocore 재시도 로직을 탐
- 막힌 점: 처음에는 핸들러가 불리지 않았음. moto도 `before-send`에서 응답을 만들어 돌려주는데, botocore는 처음 나온 응답을 쓰므로 나중에 등록한 내 핸들러까지 오지 않음. `register_first`로 moto보다 먼저 불리게 함
- 확인: 시도 횟수가 정확히 3번(실패 2번 + 성공 1번)인지 셈. `time.sleep`은 막아서 백오프 대기로 시험이 느려지지 않게 함
- 배운 점: 재시도를 시험하려면 재시도가 일어나는 층(여기서는 HTTP 응답)에서 실패를 만들어야 한다. 그보다 위에서 예외를 던지면 재시도 코드를 건너뛴다

## 4. 페이지 넘김 시험이 정말 페이지를 넘기나

- 고민: 카탈로그 조회는 1MB마다 끊겨서 `LastEvaluatedKey`로 이어 받아야 함. 항목 1,200개(항목당 약 1KB)를 넣는 시험을 만들었는데, moto가 1MB 제한을 흉내 내지 않으면 시험이 그냥 통과함
- 확인: 페이지 넘김을 일부러 끊어 봄(첫 페이지만 읽고 끝냄) → 시험 실패. moto도 1MB에서 끊는다는 것과 시험이 제 역할을 한다는 것을 같이 확인함

## 5. LocalStack을 CI에서 뺌

- 이슈: 초기 계획은 CI에서 LocalStack으로 통합 시험을 한 번 더 돌리는 것이었음. 확인해 보니 LocalStack은 2026-03-23부터 무료 이미지도 인증 토큰을 요구함
- 판단: 토큰을 저장소 시크릿으로 넣을 수는 있지만, 포크에서 온 PR에는 시크릿이 전달되지 않아 시험이 안 돎. 공개 레포의 CI가 외부 계정에 묶이는 것도 원하지 않음
- 결정: CI도 moto 서버로 함. moto와 실제 S3의 차이는 마지막에 실제 AWS에서 한 번 돌려서 기록함
- 배운 점: 계획에 넣은 도구도 쓰기 직전에 지금 조건을 다시 확인한다. 반년 사이에 무료 조건이 바뀌었음

## 6. 타입 스텁과 싸운 것

- `create_bucket`의 `LocationConstraint`는 스텁에서 리전 이름 Literal로만 받음. 클라이언트 리전은 실행 시점에야 알 수 있어서 `cast`를 쓰고 이유를 주석으로 남김
- `delete_objects`의 `Objects`는 `ObjectIdentifierTypeDef` 목록이어야 해서 변수에 타입을 적음
- 503 응답을 만들 때 헤더 자리에 `{}`를 넣으면 mypy가 `HTTPHeaders`가 아니라고 막음. `botocore.compat.HTTPHeaders()`를 씀

## 남은 고민

- 5GB가 넘는 객체: 지금은 조용히 건너뛰지 않고 멈춤. `UploadPartCopy`로 나눠 복사하면 S3가 돌려주는 체크섬은 전체 내용의 SHA256이 아니라 파트별 체크섬의 체크섬(composite)이 됨. 복구 검증 방식도 같이 바꿔야 함
- 같은 초에 생긴 두 버전: S3 `LastModified`는 초 단위라서 시점 복구 때 같은 초의 두 버전 중 무엇이 나중인지 시각만으로는 알 수 없음. 다음 PR(시점 복구)에서 정함
- 원본이 매우 클 때: 실행마다 카탈로그 전체를 읽어서 아는 버전 집합을 만듦. 객체 수억 개면 메모리와 시간이 문제임. 이벤트 방식(확장 단계)으로 가면 이 비교가 필요 없어짐
